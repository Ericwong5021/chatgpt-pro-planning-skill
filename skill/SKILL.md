# ChatGPT Pro 前期规划

把 ChatGPT Pro 当作外部规划顾问。Codex 负责收集事实、控制披露范围、操作网页、核对结果并对最终建议负责；不要把 Pro 的回答直接当成事实或最终决定。

## 适用边界

- 用户点名 `$chatgpt-pro-planning`，表示希望进入外部规划流程，但每次向网页版 ChatGPT 发送规划简报前仍须按浏览器规则即时确认。
- 如果只是被自动匹配，而用户没有明确要求调用外部模型，先说明为何建议使用本 Skill，再决定是否准备外部规划简报。
- 只做任务前期分析和规划。除非原始请求还要求继续执行，否则不要代替用户实施方案。
- 不要发送密码、令牌、Cookie、个人身份信息、未脱敏业务数据、隐藏的系统或开发者指令，也不要整份上传无关文件。敏感上下文无法安全脱敏时停止并说明缺少什么。

## 工作流程

1. 先读取当前任务与可用事实。对代码任务，至少确认相关仓库状态、现有约束、入口和已知错误；不要把猜测包装成背景事实。
2. 形成一份紧凑的规划简报，包含：目标、已知事实、约束、未知项、当前证据、期望输出和明确不做的事项。只纳入 Pro 推理必需的上下文。
3. 在任何浏览器操作前，加载并遵循 `chrome:control-chrome`。使用用户的外部浏览器插件和现有登录态，访问 `https://chatgpt.com/`；不得读取 Cookie、本地存储、密码或浏览器配置文件。
4. 为每个新任务新建独立对话，避免旧对话污染。通过实时页面结构定位控件，不依赖固定坐标或易变的 CSS 选择器。
5. 先从个人资料区域确认当前账号可见订阅标识为 `Pro`。再打开能力或模型选择器，把能力档位设置到页面提供的最高可用档，并在高级选项中读取实际模型名称与推理强度。若页面确实提供名称包含 `Pro` 的模型，优先选择它；若页面只提供技术模型名，则使用 Pro 账号下的最高能力档，并如实记录模型名和推理强度。不要把账号的 Pro 标识、升级入口或营销文字伪装成模型名称。
6. 若账号不是 Pro、无法确认最高能力档、无法读取实际模型与推理强度、浏览器插件不可用、登录被阻止，或遇到 CAPTCHA，立即停止并把可观察到的状态告诉用户。不得静默换用较低能力档、网页搜索、API 或其他浏览器。
7. 在文本进入输入框之前，向用户展示准备发送的脱敏规划简报，说明接收方是 `chatgpt.com`，并请求即时确认。用户确认前不得填写或提交；输入文本本身就属于对外传输。
8. 确认后提交规划简报，要求 Pro 区分事实、假设和建议，并给出推荐方案、备选方案、关键风险、执行阶段、验收证据和真正阻塞的问题。要求它不要执行外部操作。
9. 提交后持续监控页面状态。只要仍显示思考中、生成中或停止回答控件，就保持等待；长时间没有正文增长不等于失败。等待期间定期向用户说明仍在生成，不刷新页面、不重复提交，也不切换到低档模型。
10. 如果 Pro 在给出完整方案前提出追问，按下方“追问分流”判断是否需要人工介入。追问循环没有结束前，本次 Skill 调用仍是进行中。
11. 达到下方“完整成功判定”后，通过页面读取整份回复，包括当前视口之外的内容。若生成失败或中断，报告原始状态；只有页面明确提供针对同一回复的安全重试操作时才重试一次，并向用户说明发生过重试。重试后重新执行完整成功判定。
12. 回到当前任务证据中审查回复：指出与用户约束冲突、未经验证或不可执行的部分，保留有价值的部分，并补上 Pro 不知道的本地事实。
13. 输出整合后的前期分析与可执行计划。若原始请求包含后续实现，先把该计划作为执行依据再继续；若用户只要规划，到此停止。

## 完整成功判定

只有同时满足以下条件，才可以把一次 Skill 调用标记为完成：

- 页面上的思考中、生成中和停止回答状态已经消失。
- 最终回复正文已经出现且保持稳定，页面恢复到可继续输入的空闲状态，并出现回复操作控件或其他等价的完成信号。
- 回复没有停在半句话、错误提示、重试提示或等待必要追问答案的状态。
- 用户要求的主要分析和规划项目已经得到实质回答；只有开场承诺、思考摘要或局部章节不算完整答案。
- 已读取整份回复而不只是当前视口，并完成事实、假设、约束和可执行性的复核。

Pro 深度推理可能持续十分钟或更久。不得用固定短超时把仍在正常生成的请求判为完成或失败。若页面明确失败且一次安全重试也无法得到完整答案，应把本次调用标记为“未完成”，保留可观察证据并向用户说明阻塞；不得交付半截回答冒充成功。

## 追问分流

Pro 出现问句时，先判断它属于哪一种，不要把所有问句都转交给用户：

1. **完整答案后的可选邀请**：如果主体答案已经满足完整成功判定，末尾只是“是否需要继续细化”之类的邀请，不需要人工介入，也不需要回复，当前调用可以完成。
2. **可由现有证据回答的阻塞追问**：如果答案已经存在于用户确认发送的简报或当前任务中已验证的非敏感证据，不需要用户提供新内容。准备最短、可追溯的回复，但在文字进入 ChatGPT 输入框前仍须向用户展示准确内容并请求即时发送确认。
3. **可以用显式假设继续的非关键追问**：如果缺失信息不会改变推荐方向、风险等级或验收标准，可以要求 Pro 清楚标注假设并继续完成方案。该回复同样属于对外消息，发送前需要即时确认。
4. **必须人工介入的追问**：当问题涉及用户偏好、价值取舍、当前财务或健康数据、关系事实、未验证的外部状态、新的敏感信息、授权边界，或答案会实质改变方案时，暂停浏览器输入，保留当前对话，向用户展示 Pro 的原问题、为什么它是阻塞项，以及一个聚焦的回答请求。用户回答后，再展示准备发送的准确文本并请求即时确认。

如果 Pro 重复同一个阻塞问题、用户明确不愿提供所需信息，或现有证据无法安全回答，停止追问循环并把调用标记为“未完成”，说明缺失信息和可行的下一步；不得自行编造答案。只有追问得到适当处理并最终取得完整方案，调用才能转为完成。

## 提交给 Pro 的请求结构

按任务需要取舍，不必机械填满所有栏目：

```text
你是本任务的前期规划顾问，只分析和规划，不执行外部操作。

目标：
已知事实与证据：
约束：
未知项与当前假设：
明确不做：

请输出：
1. 对目标和成功标准的复述
2. 事实、假设、缺口的分离
3. 推荐方案及选择理由
4. 必要的备选方案与取舍
5. 分阶段执行计划和每阶段验收证据
6. 关键风险、失败模式与可观测性要求
7. 仅列出真正阻塞执行的问题
```

## 交付要求

最终结果应明确写出：确认到的 Pro 账号标识、实际模型标签、能力或推理强度、回复是否完整、采纳了哪些建议、拒绝或修正了哪些建议，以及整合后的计划。不要声称“已使用 Pro 模型”，除非页面实际显示的模型名称包含 `Pro`；当 Pro 是账号等级时，应准确表述为“使用 Pro 账号的最高可用能力”。
